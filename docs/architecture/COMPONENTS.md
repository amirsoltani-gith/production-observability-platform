# Platform Components

## Overview

The Production Observability Platform is composed of multiple independent components. Each component has a clearly defined responsibility and communicates with other services through well-established interfaces.

The platform is organized into four logical domains:

* Workloads
* Telemetry Collection
* Observability Platform
* Visualization

---

## Workloads

These are the services being monitored.

### Sample Application

#### Purpose

* Generate realistic application metrics
* Produce structured logs
* Export distributed traces
* Simulate failures for testing

---

### WordPress

#### Purpose

* Represent a traditional web application
* Demonstrate monitoring of PHP workloads

---

### Gitea

#### Purpose

* Represent an internal development service
* Provide additional telemetry sources

---

### Databases

#### PostgreSQL

Stores application data.

#### MariaDB

Supports workloads requiring MySQL-compatible databases.

---

#### Redis

Provides in-memory caching and lightweight data storage for supported workloads.

---

## Telemetry Collection

### Prometheus

#### Responsibility

* Collect metrics from exporters
* Store time-series metrics
* Evaluate alert rules

#### Consumes

* Metrics endpoints

#### Provides

* Metrics queries

---

### Node Exporter

#### Responsibility

Expose Linux host metrics.

#### Examples

* CPU
* Memory
* Disk
* Filesystem
* Network

---

### cAdvisor

#### Responsibility

Expose container-level metrics.

#### Examples

* CPU usage
* Memory usage
* Container filesystem
* Network traffic

---

### Blackbox Exporter

#### Responsibility

Monitor service availability.

#### Examples

* HTTP
* HTTPS
* TCP
* DNS

---

### OpenTelemetry Collector

#### Responsibility

Collect, process, and forward telemetry.

#### Responsibilities

- Receive telemetry
- Process telemetry
- Enrich telemetry
- Export telemetry

---

## Observability Platform

### Loki

#### Purpose

Store centralized logs.

---

### Tempo

#### Purpose

Store distributed traces.

---

### Alertmanager

#### Purpose

Route and manage alerts generated by Prometheus.

---

## Visualization

### Grafana

#### Purpose

Provide a unified interface for observing metrics, logs, traces, and alerts.

Capabilities

* Dashboards
* Metrics
* Logs
* Traces
* Alert visualization

---

## Design Principles

Every component should:

* Have a single responsibility
* Be independently replaceable
* Use open standards where possible
* Avoid unnecessary coupling
* Be documented before implementation

---

## Future Components

Additional services may be introduced during later project phases if they provide clear engineering value.

Potential future components include:

* Kubernetes
* MinIO
* Kafka
* Mimir
* Pyroscope

These components are intentionally excluded from the initial architecture to keep the platform focused and incrementally evolvable.

New components should be introduced only after documenting the architectural decision through a dedicated ADR.
